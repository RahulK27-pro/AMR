# Distributed Simulation & Autonomous Edge Architecture

## 1. Overview & Problem Definition

In an edge-based autonomous mobile robot (AMR), the onboard compute unit (e.g. Raspberry Pi 4/5) is dedicated to running the robot's autonomy stack: localization, sensor fusion, path planning, obstacle avoidance, mission management, and API servers.

### The Physics/Simulation Constraint
* In simulation, Gazebo simulates the entire physical world: rigid body dynamics, collisions, and ray-tracing for LiDAR beams.
* In Gazebo Harmonic (`gz-sim 8`), LiDAR simulation (`gpu_lidar`) is computed via depth-camera shader passes using the **OGRE 2 (`ogre2`)** rendering engine.
* Running `gpu_lidar` on a Raspberry Pi (ARM64 without desktop OpenGL 3.3 hardware) causes Mesa `llvmpipe` software rasterization to either:
  1. Overheat and throttle the 4 ARM cores at 100% CPU load, or
  2. Crash with a **Segmentation Fault (`SIGSEGV` / exit code -11)** due to shader/EGL context incompatibilities.
* When Gazebo crashes, the `/clock` topic stops. Because all ROS 2 nodes use `use_sim_time: true`, simulation time freezes and the entire robot becomes unresponsive.

### The Solution: Distributed Digital Twin (Option C)
To keep the Raspberry Pi completely safe, cool, and dedicated to autonomous brain execution:
* **The Laptop acts as the Digital Twin**: runs Gazebo Harmonic with full GPU acceleration, rendering 360° laser rays (`gpu_lidar`) at a locked 1.0 Real-Time Factor (RTF) with zero CPU lag.
* **The Raspberry Pi runs the Autonomous Edge Stack**: runs `robot_state_publisher`, `ekf_node`, `map_server`, `amcl`, `route_runner`, `bt_manager`, and the web dashboard.
* **Both machines communicate via ROS 2 CycloneDDS on Domain 7** using explicit Unicast Peer Discovery.

```
┌────────────────────────────────────────┐           ┌──────────────────────────────────────────────┐
│       💻 LAPTOP (Digital Twin)         │           │        🤖 RASPBERRY PI (Edge Brain)          │
│ • Gazebo Harmonic (GPU Acceleration)   │           │ • robot_state_publisher (URDF TF tree)      │
│ • Full 360° GPU LiDAR (gpu_lidar)      │ CycloneDDS│ • ekf_node (robot_localization)              │
```

## 2. Topic Distribution & Data Flow

| Topic | Type | Direction | Rate | Description |
| :--- | :--- | :--- | :--- | :--- |
| `/clock` | `rosgraph_msgs/msg/Clock` | Laptop ➔ Pi | 100 Hz | Simulation clock used by all nodes (`use_sim_time: true`) |
| `/odom` | `nav_msgs/msg/Odometry` | Laptop ➔ Pi | 50 Hz | Raw wheel odometry from Gazebo diff-drive plugin |
| `/imu/data` | `sensor_msgs/msg/Imu` | Laptop ➔ Pi | 50 Hz | IMU orientation & angular velocity |
| `/scan` | `sensor_msgs/msg/LaserScan` | Laptop ➔ Pi | 10 Hz | 360-ray range scan from Gazebo `gpu_lidar` |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | **Pi ➔ Laptop** | 20 Hz | Motor commands generated by MPPI `route_runner` |
| `/map` | `nav_msgs/msg/OccupancyGrid` | Internal to Pi | 0.5 Hz | Static occupancy grid from `nav2_map_server` |
| `/odometry/filtered` | `nav_msgs/msg/Odometry` | Internal to Pi | 50 Hz | Fused robot pose & velocity from `ekf_node` |
| `/amcl_pose` | `geometry_msgs/msg/PoseWithCovarianceStamped` | Internal to Pi | Event | Global map-localized pose from `nav2_amcl` |
| `/dynamic_obstacle/odom` | `nav_msgs/msg/Odometry` | Laptop ➔ Pi | 20 Hz | Live coordinates of moving warehouse obstacles |
| `/dynamic_obstacle/cmd_vel` | `geometry_msgs/msg/Twist` | Pi ➔ Laptop | 10 Hz | Patrol velocity for dynamic obstacle models |

## 3. Network Architecture (CycloneDDS Unicast)

Standard Wi-Fi networks block UDP multicast packets (IGMP snooping). CycloneDDS unicast peer configuration establishes direct UDP unicast tunnels between the two IP addresses.

### 3.1 Network Topology
* **Raspberry Pi IP**: `10.87.204.118` (or current assigned IP)
* **Laptop IP**: Detected automatically via `hostname -I` (e.g. `10.87.204.XX`)
* **ROS Domain ID**: `7`
* **RMW Implementation**: `rmw_cyclonedds_cpp`

### 3.2 Laptop CycloneDDS Peer XML (`/tmp/cyclonedds_laptop.xml`)
```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="7">
    <Discovery>
      <Peers>
        <Peer Address="10.87.204.118"/>
      </Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
```

### 3.3 Raspberry Pi CycloneDDS Peer XML (`/tmp/cyclonedds_pi.xml`)
```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="7">
    <Discovery>
      <Peers>
        <Peer Address="<LAPTOP_IP>"/>
      </Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
```

## 4. Operational Guide

### 4.1 On the Laptop (Run Virtual World)
Run the automated simulation launcher with the Pi's IP address:
```bash
cd ~/AMR/AMR-main
./launch_sim_laptop.sh 10.87.204.118
```
* Gazebo Harmonic starts with `test1.world`.
* The AGV spawns with `type="gpu_lidar"`.
* The `ros_gz_bridge` starts broadcasting `/clock`, `/odom`, and `/scan` over Wi-Fi directly to the Pi.

### 4.2 On the Raspberry Pi (Run Autonomous Brain)
Start the AMR Control Bridge and Navigation Stack in remote-sim mode:
```bash
cd ~/AMR/app/bridge
./run_bridge.sh --remote-sim
```
* The Pi connects to the incoming stream from the laptop.
* `navigation_launch.py` starts with `run_sim:=false` (no Gazebo on the Pi).
* `robot_state_publisher`, `ekf_node`, `map_server`, and `amcl` initialize.
* `route_runner` and `bt_manager` activate path planning and obstacle evasion.
* The web dashboard is accessible at `http://10.87.204.118:5173`.

## 5. Seamless Transition to Real Hardware

When physical hardware (RPLIDAR, motor controllers, wheel encoders) is connected to the Pi:
1. Stop `launch_sim_laptop.sh` on the laptop.
2. Launch the physical LiDAR driver on the Pi:
   ```bash
   ros2 launch sllidar_ros2 sllidar_launch.py serial_port:=/dev/ttyUSB0
   ```
3. Launch the motor driver on the Pi (subscribing to `/cmd_vel` and publishing `/odom`).
4. **The navigation stack, AMCL, Route Runner, and Web Dashboard require zero modifications**, because they already run entirely on the Pi.
